# MITA-OS — نسخة Inbound المستقلة

هذه نسخة ويب مستقلة مأخوذة من واجهة Inbound الحالية. تحافظ على المكوّنات والتصميم الحالي، وتستخدم Supabase كمصدر للحقيقة. يظل Figma Make بيئة التصميم والتطوير، وليس شرطًا لتشغيل التطبيق.

## النشر

- مصدر التطبيق: `frontend/`.
- فرع النشر: `mita-os-live-inbound`.
- سير العمل: `.github/workflows/pages.yml`.
- البناء: `npm run typecheck` ثم `GITHUB_PAGES=true npm run build`.
- عنوان GitHub Pages المتوقع: `https://yossefeldeep1-png.github.io/Fashion-Operations-OS/` بعد نجاح الـ Workflow وتفعيل Pages.

## العمليات الموصولة

- تسجيل الدخول واستعادة كلمة المرور عبر Supabase Auth.
- Control Tower: قراءة الوظائف والعدادات الفعلية.
- إنشاء Receipt/Job يدوي أو مرتبط بأمر شراء مفتوح باستخدام `mita_create_receipt`.
- تفاصيل الاستلام، سطور الأصناف، QC، تأكيد الاستلام وPutaway عبر RPCs تتحقق من الصلاحيات.
- Timeline وAudit من RPCs حقيقية؛ الواجهة لا تصنع أحداثًا تاريخية وهمية.
- Notes: قراءة وإضافة ملاحظات عبر `mita_get_receipt_notes` و`mita_add_receipt_note`.
- Documents: رفع إلى Bucket خاص، تسجيل عبر `mita_register_receipt_document`، واستعراض وتنزيل عبر جلسة مصرح بها.
- حالة الجاهزية تعرض نواقص الكتالوج بدل إخفائها.

## حالة بيانات الـ Master

في آخر فحص مباشر لقاعدة البيانات، لم توجد أوامر شراء مفتوحة ولا أصناف نشطة، وبعض سجلات المورد/المخزن أسماء اختبار أو مؤقتة. لذلك لا ينشئ التطبيق SKU وهميًا ولا يخترع PO. يمكن إنشاء Job بعد تأكيد المشغل أنه يقصد اختبار السجلات الحالية، لكن إضافة سطر تحتاج SKU نشطًا حقيقيًا. أضف بيانات الـ master الفعلية قبل التشغيل الإنتاجي.

بعض وحدات MITA-OS خارج Inbound، مثل Outbound وFinance، تظل غير موصولة في هذا الإصدار. الترندات التاريخية لا تعرض كأنها بيانات فعلية ما لم توفرها API موثوقة.

## إعداد Auth بعد النشر

بعد نجاح النشر، افتح Supabase Dashboard → Authentication → URL Configuration، وأضف العنوان النهائي إلى قائمة Redirect URLs. التدفق يستخدم عنوان صفحة التطبيق الحالية في طلب الاستعادة، لذلك يجب اختبار طلب الرسالة وفتح الرابط وتعيين كلمة مرور جديدة من العنوان النهائي قبل إعلان الاستعادة مكتملة.

## الأمان

- الموجود في المتصفح هو Project ID ومفتاح anon/publishable فقط.
- ممنوع وضع `service_role` أو كلمة مرور قاعدة البيانات في هذا المستودع أو أي متغير `VITE_*`.
- العمليات المعدّلة تستخدم RPCs ذات فحوص صلاحيات داخل قاعدة البيانات.
- ملفات المستندات وQC محفوظة في Buckets خاصة. لا تُعطّل RLS لمعالجة خطأ واجهة.
